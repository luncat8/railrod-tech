# 0.1.0 — dynamic tech tree, railroad prototype

Goal: a 1D wrap-X railway economy where the player's real decisions are *how to
build the train and the line*. Everything else is a live readout: the point is
to watch the net money per second react as you slide gauge, wheel diameter,
engine size and wagon count. The tech tree is not a list of unlocks — it is a
continuous parameter space with mass and cost penalties, explored directly.

Main question of the prototype: is there a realistic optimum for the build, and
does it emerge during play? A 4 m gauge and an enormous engine should lose to a
moderate build in the net number, not by decree.

Stage 0.1 = playable one-way trade loop + one train + live build knobs. Torque
realism, fuel, competitors and grade-aware movement/pathfinding are 0.2+ (see
"Deferred"); the heightmap is visual groundwork.

Parked material: `deferred-plan.md` (the old trading milestone, the auto-trader,
and the closed-form trip estimate).

## Units

Fix these before any code, they leak everywhere otherwise.

| name | meaning |
|---|---|
| km | world distance along the ring; 1 ring = `RING_KM` (default 64) |
| unit | one wagon-load of one resource; all stocks in integer-ish units |
| `UNIT_T` | mass of one unit, constant (default 12 t) |
| cr | credit, money. Money is unbounded: only rates are read |
| t | mass, tonnes |
| s | sim second, fixed `DT = 1/60` |

Speeds are *visual* speeds (km/s ≈ 1–3), not physical. No km/h anywhere.

## Core loop

```
source nodes fill stock ──> price falls there
consumer nodes drain stock ──> price rises there
price gradient between nodes = margin
train carries units from a cheap source to a consumer that needs them
margin collapses at both ends ──> the economy breathes
```

The train runs one way around the loop and stops only where a stop pays. The
player watches the economy breathe and tunes the machine that harvests it. A
slow train misses stops; a heavy train cannot brake and accelerate out of them
fast enough; an expensive build never recovers its capital. That is the game.

## World

- 1D ring, `x` in `[0, RING_KM)`, wraps. Side view only.
- `NODE_N` nodes placed on the ring at generation (default 14), min spacing
  `MIN_GAP_KM` so no two stops overlap.
- distance `D(a,b) = min(|a-b|, RING_KM - |a-b|)`. The train's own direction is
  always `+x`, so the forward distance from one node to the next is
  `wrap(x_b - x_a)`.
- node kinds: `SRC` (emits one resource), `CON` (consumes a recipe). `MIX`
  (emits two, consumes one) is added at 0.1.6 if the world feels flat.
- resources: `R1, R2, R3` only. 3 colors, 3 bars, done.

Node state (flat typed arrays, index `i*RES + r`):

```
stock[i*3+r]   units present in the node yard
cap[i*3+r]     yard capacity
inflow[i*3+r]  SRC: units/s emitted (overflow is lost, not stored)
produced[i*3+r] ledger: total inflow ever emitted (for the mass-balance check)
```

Recipes are a 3-bit mask + a consumption rate:

```
need[i]   bitmask, e.g. 0b011 = consumes R1 and R2 together
rate[i]   baskets/s the consumer can eat
```

A consumer eats one basket per `1/rate` seconds only if *all* masked stocks have
at least one unit; otherwise it stalls. Stalling is the whole reason combos are
interesting: a half-fed consumer stops buying, its stock stays high, its price
collapses, and an unbalanced trader visibly starves. No special-casing needed.

## Economy

Single value curve per node/resource, buy and sell are a band around it:

```
fill  f(s) = clamp(s/cap, 0, 1)
p(i,r,s) = base(i,r) * (FLOOR + (1-FLOOR) * pow(1-f(s), k_i)) // FLOOR=0.2
buy(i,r,s)  = p(i,r,s-0.5) * (1 + SPREAD) // one unit moves s → s-1
sell(i,r,s) = p(i,r,s+0.5) * (1 - SPREAD) // one unit moves s → s+1
```

- `SPREAD` default 0.08. Unit quotes use the midpoint of the stock interval
  crossed, so buying and immediately selling the same unit at the same node
  uses the same underlying `p` and necessarily loses the spread. Transport is
  the only source of profit; this invariant kills most exploit classes.
- `k_i` is the node's fragility: 0.5 = tolerant flat market, 2 = steep, a small
  delivery crashes the price. Randomized per node at world gen; it is the
  readable difference between "good" and "difficult" nodes.
- Trade is unit-by-unit (see the train section). Quote the midpoint price for
  the stock interval crossed, mutate stock, then quote the next unit. Never
  apply one stale bulk quote to several wagons; that would let large trains
  evade their own price impact.
- Inflow is recorded in `produced` before overflow is taken, so
  `produced = Δstock + overflow` for a source at every tick.

Stock feedback is what makes the sim alive: unloading raises `f` at the
destination and lowers it at the origin, so the same trip repeated twice is
already worse. That decay is what makes the economy breathe.

## Train

One train: `loco` + `W` wagons (player slider, 1..8). Each wagon carries at most
one whole unit of one resource (`-1` means empty; `0..RES-1` are cargo). `UNIT_T`
is cargo mass, not wagon tare; loaded cargo contributes to train mass. Gauge and
wheel settings affect the wagon itself, never the one-unit payload.

### Movement rule

- The train runs `+x` only and wraps at the seam. It never reverses and has no
  destination; route clicks are gone.
- It brakes for the nearest node ahead that *wants* a stop and stops there;
  unwanted nodes are passed at speed.
- A node wants a stop if the train can unload there (carried `r` in the node's
  recipe, room for one unit) or the train can load there (a free wagon and a
  source with a unit of `r` at a positive margin over the best downstream sell).
- Braking: the train's speed is capped by `min(vTrack, sqrt(2 · BRAKE_DECEL · d))`
  for the distance `d` to that stop. Above the cap it brakes at
  `max(BRAKE_DECEL, v² / 2d)`, which stops it exactly at the node; below the cap,
  traction and resistance act.
- Arrival is captured inside the step that covers the distance. A stop that
  moves nothing is not a stop: the train departs without dwelling.
- Dwell is transfer-driven: `units moved / UNITS_PER_S`.

### Trade at a stop

- Unloads first (wagon-index order), then loads into the freed and empty wagons
  (wagon-index order).
- Sell to a consumer: `sell(i,r,s)` per unit; loading buys at `buy(i,r,s)` per
  unit, only at a positive margin. Consumers never sell and sources never buy
  back in 0.1.4 (see `deferred-plan.md`).
- Train cash is a running total. The profit rate is an EMA of the change in it.

Kinematics (the stand-in for the deferred torque model — it costs one function
and already produces the emergent limits we want):

```
M     = m_loco + W * m_wagon + cargoUnits * UNIT_T   // t
F(v)  = min(F_trac, P / max(v, v_eps))              // t·km/s²
F_res = c_rr * M * G + c_drag * v³
a     = (F - F_res) / M
```

Compute the force model once per train per step; the signed acceleration lets
resistance slow the train instead of freezing velocity when force runs out.
Units are internally consistent, never SI.

- `F_trac = MU * DRIVE_SHARE * m_loco * G` — traction is limited by *adhesive
  weight only*, so an over-wagoned train physically cannot leave a station
  fast. That is the mass-vs-performance story the player feels.
- A braking envelope belongs to the movement rule above, not to the force model;
  the torque model in 0.2 replaces both.

## Tech knobs

Three sliders, each `t ∈ [0,1]`, each a triple of curves. Defaults are the
starting build; nothing is unlocked, everything is traded off.

| knob | performance up | cost / mass up |
|---|---|---|
| gauge `g` | `v_track`, curve speed limit | track `cr/km` ∝ g², wagon tare |
| wheel `d` | lower `c_rr`, slightly higher `v_track` | rotating mass and wheel cost ∝ d² |
| engine `e` | `P`, `F_trac` (driven axle load) | `m_loco` ∝ e, `cr` ∝ e^1.5 |

```
v_track        = V0 * (0.7 + 0.6g) * (0.9 + 0.2d)
m_wagon        = M0 * (0.8 + 0.4g) + MW * d*d
track/km       = K_TRACK * (0.6 + 1.4*g*g)
c_rr           = C_RR0 * (1.3 - 0.7d)
P              = P0 * pow(0.15 + 0.85e, 1.8)
m_loco         = ML * (0.5 + e)
wagon_cost     = CW * (0.7 + 0.6g + 0.8*d*d)
loco_cost      = CL * pow(0.15 + 0.85e, 1.5)
```

Readouts in physical units, shown next to each slider: gauge `0.6 + 3.4g` m, wheel
`0.4 + 1.2d` m, engine `m_loco` t.

`m_wagon` includes an equivalent rotational-mass penalty from the wheels;
`cargoUnits * UNIT_T` is accounted separately in train mass. This keeps wheel
size's speed/resistance benefit in tension with its inertia and cost.

### Capex as a rate

Money is unbounded, so the build's capital is not a one-off charge. It is
amortised over `AMORT_S`, which makes the net number a steady-state efficiency
and removes the transient a one-time charge would cause:

```
buildValue = RING_KM * track/km(g) + W * wagon_cost(g,d) + loco_cost(e)
capexRate  = buildValue / AMORT_S
```

The loop is the route, so the track term is the full ring and does not depend on
where the train stops. `AMORT_S` is a price of capital: changing it moves where
the optimum sits, so it is part of the design, tuned by experiment and shown as
a readout, not hidden. Constant knobs are in one table in `const.js` and tuned
by experiment, not by hand in the render loop.

### Profit metrics

```
profitRate = EMA over PROFIT_TAU_S (60 s, about one loop) of the train's cash flow per second
netRate    = profitRate - Σ capexRate
```

`netRate` is the y-axis of the game. Show `profitRate` and `capexRate` next to
it so the player sees where the difference comes from.

### Performance plot

The draft says "plot size (performance) vs mass (cost)". Concretely: a small square
panel, x = total train mass, y = net money per second. It is added at 0.1.5.

- faint dots: a headless sweep over a 9×9×3 grid of `(g,d,e)` → measured
  `netRate`, recomputed once per knob change (never per frame);
- crosshair: the current build, placed by live `netRate` next to the dot for
  the same combo.

The gap between the grid's best and the live crosshair is the content: the
player sees where the real optimum lies and how far off they are.

## Architecture

Classic scripts, `file://` friendly, no build, one namespace `RR`. Every file
guarded so `require()` works under node:

```
if (typeof module !== 'undefined') module.exports = RR.tech;
```

```
index.html
	js/rng.js        seedable PRNG (mulberry32), world gen + all noise
	js/const.js      units, defaults, the knob curve constants
	js/world.js      ring layout, node + recipe generation → flat arrays
	js/economy.js    price curves, source/consumer tick, produced ledger
	js/tech.js       knobs → build, readouts, capex rate
	js/trade.js      wanted-ness, margin, unit transfers at a stop
	js/train.js      loop movement, braking envelope, stop scan, dwell
	js/sim.js        owns state, game tick, profit and net rates
	js/clock.js      fixed-step accumulator, time scale, step cap
	js/render.js     canvas 2D, camera, reads sim only, writes nothing
	js/ui.js         HUD + sliders, dispatches intent to sim
	js/main.js       boot, rAF, step budget
experiments/       node scripts: unit checks, mass balance, sweeps
archive/           completed plans and worklogs
```

Dep order is the list order; no cycles; `sim.js` never touches DOM, `render.js`
never mutates sim state. That boundary is what makes the node experiments
possible.

State is preallocated at world gen: `Float32Array` for stocks/prices,
`Int8Array` for masks and wagon cargo, one `sim` object reused forever. Per
frame: no `new`, no closures, no string concat — the HUD writes DOM text at a
throttled 4 Hz and only when a displayed value changes. A build object is
allocated only when a knob changes, never per step.

`DT` never changes. The accumulator is measured in simulation seconds, so time
scale is independent of display refresh rate:

```
frameDt = min(max((now - previous) / 1000, 0), MAX_FRAME_SECONDS)
acc += frameDt * speed
acc = min(acc, DT * MAX_STEPS)
while (acc >= DT && steps < MAX_STEPS) { sim.step(DT); acc -= DT; steps += 1; }
```

Use `MAX_FRAME_SECONDS = 0.25`, `MAX_STEPS = 30`, and speed in `[0.25, 8]`.
Record the sim-time discarded by either clamp for the HUD; do not carry a large
backlog into the next frame. Never multiply `DT` by speed. Given the same seed
and exact number of fixed steps, sim and RNG state must match at every speed;
wall-clock time and `Math.random` must never affect game state.

## UI

No sub-menus, no modal. Two strips and the canvas.

- top: seed, speed, pause (as now).
- bottom, left: `BUILD` group — `WAGONS 1–8`, `GAUGE m`, `WHEEL m`, `ENGINE t`.
- bottom, telemetry: `NET/S` (accented), `PROFIT/S`, `CAPEX/S`, `TRAIN SPEED`,
  `CARGO loaded/W`, render/sim/steps/dropped.
- world: no route clicks. Hover a node to read its three prices and stock as a
  floating label only. The train shows its cargo as coloured wagons and a dwell
  bar at stops.

Colors: R1 amber, R2 slate-blue, R3 teal; background 2 flat tones (sky, ground).
Node = silhouette + 3 vertical stock bars + price ticks. Train = loco + N rects.
Every number that matters is visible without interaction, including while a
knob is being dragged.

## Experiments (node, no page)

```
experiments/train.js            the movement rule: stops, braking, dwell, one direction
experiments/trade.js            margin, unit transfers, cash, profit EMA
experiments/mass-balance.js     produced ledger identity across seeds
experiments/tech.js             knob bounds, default build, readouts, capex monotone
experiments/surface.js          (0.1.5) grid of (g,d,e) → measured netRate, headless
```

`experiments/surface.js` is how 0.1.5 is tuned — headless sim, one number per
combo, no rendering. If a combo is best on the analytic plot but never best in
the sim, either the plot is lying or the dwell model is; find out which.

## Deferred (0.2+)

Shape the code now so these are additive, do not implement them early. Parked
trading and planner material is in `deferred-plan.md`.

- **torque/speed realism** (RT3-flavoured, emergent not licensed): replace the
  `F(v)` line with a torque curve per gear; keep `train.step` a pure function of
  `(state, forces)` so nothing else changes.
- **brakes as a knob**: braking capacity currently constant; a brake knob would
  make the stopping envelope part of the build.
- **fuel**: the train consumes a resource and buys it automatically → reuse the
  node price model with the train as a node; keep `trade.js` separate from
  `kinematics` for exactly this.
- **sources buying back, and a planner** (see `deferred-plan.md`).
- new game mode: **competitor trains** on the same line, pushing each other / reversing at the
  wrap. Requires: train state as an indexed pool (already `sim.trains[]`), a
  per-segment occupancy/lock table, and block times.
- **bot tactics** vs the player (route denial, camping a node) — needs scoring
  kept pure in a planner module.
- **grade resistance and pathfinding over the heightmap**: `world.terrain[i]`
  and the side-view height/slope rendering are in place as visual groundwork.
  When grades enter kinematics, make speed caps and resistance per segment rather
  than extending the current scalar `v_track`.

## Non-goals

No save/load, no menus, no audio, no mobile-specific layout, no multi-line
network, no market news/events, no art pipeline. No compatibility layer for
anything removed at the previous milestone.

## Risks

| risk | mitigation |
|---|---|
| same-node arbitrage or unbounded trade exploit | midpoint unit quotes plus `SPREAD` make round trips lose; full yards reject deliveries; the production ledger is checked every run |
| the margin rule trades at a price the loop later undercuts (naive bias) | measured in `trade.js`; the parked planner is the fix, not a hidden tweak |
| the optimum is a boundary, not an interior point (the knobs are monotone) | `AMORT_S` and cost constants are part of the design; 0.1.5 checks interiority on several seeds before any tuning is called done |
| economy settles to flat prices → game dies boring | per-node `k_i` fragility + inflow jitter; watch for total-margin collapse and log it |
| numbers tuned by eye in the browser | tune in headless experiments, confirm visually |
| wrap math bugs at the seam | all positions stored unwrapped for the camera, wrapped only for lookup; experiments cross the seam |
| a stop appears inside braking distance and the train overshoots | wanted-ness changes slowly, so the envelope is always met in practice; the capture snaps any residual overshoot and experiments record its size |

## Open questions

1. Capex as an amortised rate over `AMORT_S`, not a one-off charge: is the
   horizon the right price of capital, or should the amortisation scale with the
   stage? Default: 1200 s, provisional.
2. Scoring: prototype has no win state — is `netRate` enough of a goal, or do we
   want a soft target (e.g. `netRate` above a line for N seconds)?
3. Wagon granularity: 1 unit per wagon keeps the picture honest but caps trade at
   `W` units per stop; if trips become trivially short, switch to fractional
   per-wagon fill and show a fill bar instead.
4. Track cost is a loop-wide constant. If the player may later build a partial
   line, the route length returns as a term; keep `RING_KM` in the formula.
