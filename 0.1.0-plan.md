# 0.1.0 — dynamic tech tree, railroad prototype

Goal: a 1D wrap-X railway economy where the player's only real decisions are
*where to run the train* and *how to build it*. Everything else is a live
readout: the whole point is to watch profit/sec react while you slide gauge,
wheel diameter and engine size. The tech tree is not a list of unlocks — it is
a continuous 3-axis parameter space with mass/cost penalties, explored
directly.

Stage 0.1 = playable economy + one train + tech knobs. Torque realism, fuel,
competitors, heightmap are 0.2+ (see "Deferred").

## Units

Fix these before any code, they leak everywhere otherwise.

| name | meaning |
|---|---|
| km | world distance along the ring; 1 ring = `RING_KM` (default 64) |
| unit | one wagon-load of one resource; all stocks in integer-ish units |
| `UNIT_T` | mass of one unit, constant (default 12 t) |
| cr | credit, money |
| t | mass, tonnes |
| s | sim second, fixed `DT = 1/60` |

Speeds are *visual* speeds (km/s ≈ 1–3), not physical. No km/h anywhere.

## Core loop

```
source nodes fill stock ──> price falls there
consumer nodes drain stock ──> price rises there
price gradient between nodes = margin
train moves units from cheap to expensive ──> margin collapses at both ends
train re-plans ──> the economy breathes
```

The player watches that breathing and tunes the machine that harvests it. If
the train is too slow it misses the peak margin; too big and it cannot
accelerate out of a stop before the next one. That is the entire game.

## World

- 1D ring, `x` in `[0, RING_KM)`, wraps. Side view only.
- `NODE_N` nodes placed on the ring at generation (default 14), min spacing
  `MIN_GAP_KM` so no two stops overlap.
- distance `D(a,b) = min(|a-b|, RING_KM - |a-b|)`; direction = the shorter arc,
  tie (exactly antipodal) → increasing x. Never ambiguous at runtime.
- node kinds: `SRC` (emits one resource), `CON` (consumes a recipe),
  `MIX` (emits two, consumes one — added after 0.1.2 if the world feels flat).
- resources: `R1, R2, R3` only. 3 colors, 3 bars, done.

Node state (flat typed arrays, index `i*RES + r`):

```
stock[i*3+r]   units present in the node yard
cap[i*3+r]     yard capacity
inflow[i*3+r]  SRC: units/s emitted (overflow is lost, not stored)
```

Recipes are a 3-bit mask + a consumption rate:

```
need[i]   bitmask, e.g. 0b011 = consumes R1 and R2 together
rate[i]   baskets/s the consumer can eat
```

A consumer eats one basket per `1/rate` seconds only if *all* masked stocks have
at least one unit; otherwise it stalls. Stalling is the whole reason combos are
interesting: a half-fed consumer stops buying, its stock stays high, its price
collapses, and an unbalanced trader visibly starves. No special-casing needed.

## Economy

Single value curve per node/resource, buy and sell are a band around it:

```
fill  f = clamp(stock/cap, 0, 1)
p(i,r) = base(i,r) * (FLOOR + (1-FLOOR) * pow(1-f, k_i))     // FLOOR=0.2, k_i in [0.5, 2]
buy(i,r)  = p * (1 + SPREAD)      // player pays to lift a unit here
sell(i,r) = p * (1 - SPREAD)      // player is paid to drop a unit here
```

- `SPREAD` default 0.08 → trading at the *same* node is always a loss, so the
  only profit is transport. This one invariant kills most exploit classes.
- `k_i` is the node's fragility: 0.5 = tolerant flat market, 2 = steep, a small
  delivery crashes the price. Randomized per node at world gen; it is the
  readable difference between "good" and "difficult" nodes.
- Delivery is paid per unit at the moment of unloading, at `sell(i,r)`. Sources
  will buy back too (at their low price) — no rules needed, it is just never
  worth it.

Stock feedback is what makes the sim alive: unloading raises `f` at the
destination and lowers it at the origin, so the same trip repeated twice is
already worse. That decay is the timer that forces re-planning.

## Train

One train: `loco` + `W` wagons (player slider, 1..8). A wagon carries exactly
1 unit of one resource and weighs `UNIT_T` regardless of any knob — the picture
and the math stay one-to-one. In v0 gauge buys speed, mass and cost, *not*
payload; payload per wagon only becomes a lever if open question #3 is taken.

State machine, deliberately tiny:

```
CRUISE ──arrive──> DWELL ──plan──> CRUISE
                     │
                     └── (manual mode: no plan, fixed pair)
```

- `DWELL`: transfer rate `UNITS_PER_S` (default 2). Load and unload happen
  concurrently across wagons; visually the wagon bar fills.
- Waypoints: player clicks node A then node B (1 line, 1 train). Manual mode
  shuttles A↔B forever, trading whatever is profitable at both ends.
- Auto mode (0.1.5): the planner replaces "the other waypoint" with a scored
  choice; the manual mode is the same code path with a forced destination, so
  there is exactly one trader implementation.

Kinematics (this is the simplified stand-in for the deferred torque model — it
costs one function and already produces the emergent limits we want):

```
M     = m_loco + W * m_wagon                // t
F(v)  = min(F_trac, P / max(v, v_eps))      // t·km/s², force in abstract sim units
F_res = c_rr * M * G + c_drag * v³
a     = max(0, (F - F_res) / M),  v = min(v + a*DT, v_track)
```

All four are one function, no branches per wagon, evaluated once per train per
step. Units are internally consistent, never SI.

- `F_trac = MU * DRIVE_SHARE * m_loco * G` — traction is limited by *adhesive
  weight only*, so an over-wagoned train physically cannot leave the station
  fast. That is the mass-vs-performance story the player feels.
- Closed form trip time (needed by the planner *before* the trip):
  `t(L) = sqrt(2L/a0)` if `v_track` is not reached, else `v/a0 + (L - v²/2a0)/v`.
  Never estimate a trip by integrating a loop during planning.

## Tech knobs

Three sliders, each `t ∈ [0,1]`, each a triple of curves. Defaults are the
starting build; nothing is unlocked, everything is traded off.

| knob | performance up | cost / mass up |
|---|---|---|
| gauge `g` | `v_track`, curve speed limit | track `cr/km` ∝ g², wagon mass |
| wheel `d` | lower `c_rr`, higher top speed | rotating mass (accel penalty), `cr` |
| engine `e` | `P`, `F_trac` (driven axle load) | `m_loco` ∝ e, `cr` ∝ e^1.5, `c_rr` via mass |

```
v_track        = V0 * (0.7 + 0.6g)          m_wagon  = M0 * (0.8 + 0.4g)
track/km       = K0 * (0.6 + 1.4g*g)        c_rr     = R0 * (1.3 - 0.7d)
P              = P0 * pow(0.15 + 0.85e, 1.8)
m_loco         = ML * (0.5 + e)             accel ×  = (0.9 + 0.3d)
units/wagon    = 1                          // fixed, see open question 3
```

Capex, charged when the knob changes (delta cost, live — this is why the
player hesitates):

```
CAPEX = length(A,B) * track/km(g) + W * wagon_cost(g) + loco_cost(e, d)
```

`profit/s` is the y-axis of the game; `payback = CAPEX / profit/s` is the real
score and is shown next to it. Constant knobs are in one table in `tech.js` and
tuned by experiment, not by hand in the render loop.

### Performance plot

Draft says "plot size (performance) vs mass (cost)". Concretely: a small square
panel, x = mass or `cr`, y = performance.

- faint dots: an analytic sweep over a 9×9×3 grid of `(g,d,e)` → estimated
  `profit/s` upper bound, drawn once per knob change (not per frame);
- crosshair: the current build, placed by *measured* `profit/s` from the live
  sim, with the dot for the same combo drawn nearby.

The gap between the promise-dot and the live crosshair *is* the interesting
content (dwell, travel, and thrash eat the theoretical margin). Recompute the
sweep on demand only; never per frame.

## Auto-trader

Runs at the end of `DWELL`, so O(NODE_N * RES) work per stop — allocation is
acceptable here (still reuse a scratch struct).

```
for each candidate dest B, for each resource r:
	margin(i,r) = sell(B,r) - buy(i,r)
	weight(i,r) = margin / max(1, trip_time_est(i,B)/DT + dwell_units)
fill the free wagons greedily with (B,r) pairs by weight, best first
trip = argmax over B of  Σ_r units_r * margin(i,r,B) / t_trip(i,B)
```

- Sources can be destinations and consumers can be origins; the score decides,
  no kind-based pruning (it would just hide bugs).
- Prices are read at plan time and assumed static during the trip. Known
  naive-planner bias; do not "fix" it until the profit curve proves thrash.
- Hysteresis: keep the current plan unless a candidate beats it by 10%. Without
  this the bot oscillates between two near-equal nodes and burns dwell time.

## Architecture

Classic scripts, `file://` friendly, no build, one namespace `RR`. Every file
guarded so `require()` works under node:

```
if (typeof module !== 'undefined') module.exports = RR.tech;
```

```
index.html
	js/rng.js        seedable PRNG (mulberry32), world gen + all noise
	js/const.js      units, defaults, the knob curve table
	js/world.js      ring layout, node + recipe generation → flat arrays
	js/economy.js    price curves, source/consumer tick
	js/train.js      kinematics, state machine, load/unload, cash
	js/planner.js    greedy destination + basket choice
	js/tech.js       knobs → perf/mass/cost, capex, plot sweep data
	js/sim.js        owns state, fixed-step tick, profit/s averaging
	js/render.js     canvas 2D, camera, reads sim only, writes nothing
	js/ui.js         HUD + sliders, dispatches intent to sim
	js/main.js       boot, rAF, step budget
experiments/       node scripts: curves, mass balance, planner traces
archive/           completed plans
```

Dep order is the list order; no cycles; `sim.js` never touches DOM, `render.js`
never mutates sim state. That boundary is what makes the node experiments
possible.

State is preallocated at world gen: `Float32Array` for stocks/prices,
`Int8Array` for masks and wagon cargo, one `sim` object reused forever. Per
frame: no `new`, no closures, no string concat — the HUD writes DOM text at a
throttled 6 Hz and only when a value moved more than its epsilon.

Fixed `DT`, and game speed multiplies *steps per frame*, never `DT`:

```
acc += speed; while (acc >= 1) { sim.step(DT); acc -= 1; }
```

so an 8× run is bit-identical to a 1× run at 8× the frames. `MAX_STEPS` per
frame (default 8× speed's worst case, e.g. 30) is a hard cap: a laggy tab runs
the game slower, never stalls it. Deterministic seed + the same step count must
give the same cash. If it doesn't, something in `sim` reads wall-clock time or
`Math.random`.

## UI

No sub-menus, no modal. Two strips and the plot.

- top: `cash` `profit/s` `payback` `speed ▮▮▮▯` `⏸` `seed` (click = new world)
- bottom: `wagons ▮▮▮▯▯` `gauge` `wheel` `engine` `auto ○/●`
- world: click a node = set waypoint A, click another = B; click the line = drag
  the route; hover a node shows its 3 prices as a floating label only.

Colors: R1 amber, R2 slate-blue, R3 teal; background 2 flat tones (sky, ground).
Node = silhouette + 3 vertical stock bars + price ticks. Train = loco + N rects.
Every number that matters is visible without interaction, including while the
knob is being dragged.

## Milestones

Each is playable and checkable in the browser or a node script; do not merge two.
Milestone numbers double as file numbers: when one starts, its section here is
expanded into `0.1.N-plan.md`; when it finishes, that plan plus
`0.1.N-worklog.md` move to `archive/`. This file stays the parent reference for
the whole stage.

**0.1.0 — harness.** `index.html` gains the two HUD strips and the script tags
in dep order; canvas fills the window, DPR-correct; fixed-step loop; FPS and
step counter in a corner; seeded RNG.
*Check:* the same seed + the same 30 000 steps produce an identical RNG stream
at 1× and at 8×; tab away and back — no spiral of death (`acc` clamped,
`MAX_STEPS` respected).

**0.1.1 — ring + world gen + camera.** nodes on a ring, spacing enforced,
camera follows the train anchor (train drawn as a placeholder rect moving at
constant v).
*Check:* wrap seam is invisible — an object crossing x=0 continues off the other
side with no jump; regenerate 100 seeds, no node pair closer than `MIN_GAP_KM`.

**0.1.2 — economy, no train.** tick inflow/consumption, price curves, node bars
+ hover labels, `economy.js` unit-checked in node.
*Check:* a full stockyard stays at `FLOOR` price and overflows (lost units
accounted); a starved consumer stalls and its bars freeze; prices never exceed
`base*(1+SPREAD)` nor go below 0.

**0.1.3 — train kinematics.** waypoint selection, state machine, accel from the
force model, dwell animation. No money.
*Check:* doubling `W` visibly lengthens the trip; `t_trip` measured in sim
matches the planner's closed-form estimate within 10% (log both).

**0.1.4 — trading + profit.** load/unload against prices, cash, profit/sec
(EMA over a 10 s window), wagons slider, capex on route length only.
*Check:* mass balance — `Σ stock + Σ train units + produced − consumed == 0`;
running the same A↔B pair converges to zero margin (that is correct, not a bug).

**0.1.5 — auto-trader + speed slider.** greedy planner, hysteresis, `auto`
toggle, game speed 0.25–8×.
*Check:* auto ≥ manual profit/s on 20 seeds (the bot must not lose to the fixed
pair it was built from); zero oscillation: no destination change within 2 s of
the last one.

**0.1.6 — dynamic tech (the point).** three knobs live, mass/traction model,
capex by knob delta, perf plot panel.
*Check:* for a fixed world, the measured `profit/s` surface over the 9×9×3 grid
has a single interior maximum in the *net* objective (profit/s scaled by
payback) at ≥3 of 5 seeds; a train over its traction limit crawls out of the
station instead of snapping to speed; changing a knob mid-run never jumps prices
or stock.

**0.1.7 — tuning + world legibility.** constants table tuned via experiments,
`MIX` nodes if needed, seed field, a one-line legend, `findings-pitfalls-skills.md`
entries.
*Check:* a first-time player reaches "I see why this node is worth more" within
the first minute; every constant in `const.js` is either used or deleted.

## Experiments (node, no page)

```
experiments/curves.js       print profit/mass/cost tables for the knob sweep, sanity-check monotonicity
experiments/mass-balance.js N seeds × M ticks, assert unit conservation exactly
experiments/planner-trace.js dump one decision: candidates, margins, scores, chosen
experiments/surface.js      grid of (g,d,e) → measured profit/s with the sim headless
```

`experiments/surface.js` is how 0.1.6 gets tuned — headless sim, one number per
combo, no rendering. If a combo is best on the analytic plot but never best in
the sim, either the plot is lying or the dwell model is; find out which.

## Deferred (0.2+)

Shape the code now so these are additive, do not implement them early.

- **torque/speed realism** (RT3-flavoured, emergent not licensed): replace the
  `F(v)` line with a torque curve per gear; keep `train.step` a pure function of
  `(state, forces)` so nothing else changes.
- **fuel**: the train consumes a resource and buys it automatically → reuse the
  node price model with the train as a node; keep `load/unload` separate from
  `kinematics` for exactly this.
- **competitor trains** on the same line, pushing each other / reversing at the
  wrap. Requires: train state as an indexed pool (no single `train` object), a
  per-segment occupancy/lock table, and block times. Reserve the API now:
  `sim.trains[i]` array shape even at length 1.
- **bot tactics** vs the player (route denial, camping a node) — needs the
  planner to score *opponent* arrival, so keep scoring in `planner.js` pure.
- **heightmap** + pathfinding over it: only touches `world.js` (add `terrain[i]`)
  and `v_track`/`a` (grade resistance). Keep `v_track` a per-segment array from
  the start, not a scalar, or this will hurt.

## Non-goals

No save/load, no menus, no audio, no mobile-specific layout, no multi-line
network, no market news/events, no art pipeline. No compatibility layer for
anything removed at the previous milestone.

## Risks

| risk | mitigation |
|---|---|
| margin exploit: infinite money from two free sources | `SPREAD`, capacity overflow loss, dwell cost per unit; profit must decay to 0 on any fixed pair |
| bot thrash between near-equal nodes | 10% hysteresis + plan locked during a trip |
| economy settles to flat prices → game dies boring | per-node `k_i` fragility + inflow jitter (slow sine + noise); watch for total-margin collapse and log it |
| knobs are strictly better = no choice | every knob must have a curve that is *not* monotone in net value (mass→traction, capex→payback); verify in `experiments/surface.js` |
| numbers tuned by eye in the browser | tune in headless experiments, confirm visually |
| wrap math bugs at the seam | all positions stored unwrapped for the camera, wrapped only for lookup; assert once per frame in dev flag |

## Open questions

1. Route building: is the line cost paid per km (as assumed, `length*track/km`)
   or is track free and gauge only affects the train? Paid capex is what makes
   the gauge knob hurt, so it is the default here.
2. Scoring: prototype has no win state — is `payback` enough of a goal, or do we
   want a target "reach payback < 60 s" as a soft win line?
3. Wagon granularity: 1 unit per wagon keeps the picture honest but caps margin
   at `W` units/trip; if trips become trivially short, switch to fractional
   per-wagon fill and show a fill bar instead.
4. Manual mode as a teaching tool or as the intended play? Assumed: manual
   exists so the player can *feel* the bot's advantage, then auto is normal.
